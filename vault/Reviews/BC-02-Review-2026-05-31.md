## Executive Summary

The BC-02 implementation is **substantially complete** at the domain and application layers. The aggregate model, domain invariants, value objects, domain services, persistence mappings, and unit-test coverage are all well-executed and faithful to the spec. However, **9 gaps** were identified — 4 are blockers that prevent the module from being production-ready or contract-compliant with peer BCs.

## Gaps

### 🔴 GAP-1 — `UpdateEmployerProfileCommand` is missing

**Spec ref:** §10.1 (`UpdateEmployerProfileCommand`), §12 (`PUT /api/employers/me`)

The domain aggregate has `UpdateCompanyInformation(...)` correctly implemented, but there is no command, handler, validator, or HTTP endpoint wired for it. The `EmployerEndpoints.cs` has no `MapPut("me", ...)` route.

**Impact:** Employers cannot edit their profile after activation. User story US-3.1.2-03 AC-08 is completely unmet.

---

### 🔴 GAP-2 — `GetEmployerJobPostingsQuery` is missing

**Spec ref:** §10.2 (`GetEmployerJobPostingsQuery`), §12 (`GET /api/employers/me/dashboard/postings`)

No query, handler, or endpoint exists for returning the employer's job-posting list from the `dashboard_postings` projection.

**Impact:** The employer dashboard postings tab is non-functional. US-3.1.2-04 AC-02 is unmet.

---

### 🔴 GAP-3 — `EmployerProfilePublicApi` contract surface is absent

**Spec ref:** §9.3, §3 (module public surface)

The spec requires a `Contracts` project exposing `IEmployerProfilePublicApi` with `IsVerified(employerUserId: Guid) → bool` and `GetSummary(employerUserId: Guid) → EmployerProfileSummaryDto?`. This is the interface BC-4 (Job Postings) must call to enforce the "must be verified to publish a job" gate. Neither the Contracts project nor the interface exists.

**Impact:** BC-4 cannot enforce the verified-employer gate. The cross-module contract is broken at the composition root.

---

### 🔴 GAP-4 — Outbox + Inbox infrastructure is absent

**Spec ref:** §6 (cross-cutting conventions), §11 (persistence — `outbox_messages`/`inbox_messages`), §13.3 (integration tests)

The `EmployerProfilesDbContext` does not implement `IOutboxInboxDbContext`. There are no `OutboxMessage` or `InboxMessage` DbSets. Integration events published by this module are dispatched in-process via `PublishDomainEventsInterceptor` — they are not transactionally written to an outbox, so they will be silently lost on a process crash between `SaveChanges` and in-memory publish.

Event consumers (`EventConsumers.cs`) have no inbox deduplication — delivering the same consumed event twice will cause duplicate state changes or duplicate projection rows.

**Impact:** At-least-once delivery guarantee is broken both outbound and inbound. All spec AC relating to event-driven state transitions (verification, dashboard projections) are unreliable in production.

---

### 🟠 GAP-5 — Optimistic concurrency tokens are not configured

**Spec ref:** §11.2

Both `employer_profiles` and `shortlists` require optimistic-concurrency tokens. Neither `EmployerProfileConfiguration` nor `ShortlistConfiguration` configures `IsConcurrencyToken()` or a row-version column. Concurrent mutations (e.g. an admin suspending a profile while the employer updates it) will silently overwrite each other.

---

### 🟠 GAP-6 — Admin verification endpoints do not enforce `users:manage` permission

**Spec ref:** §12 (approve/reject require `users:manage` permission)

`GetAdminId()` in `EmployerEndpoints.cs` only checks for the presence of any `NameIdentifier` claim — every authenticated user passes. There is no `.RequireAuthorization("users:manage")` or equivalent claim/policy check. Any authenticated employer, job-seeker, or third-party portal user can call `POST /api/employers/{id}/verification/approve`.

---

### 🟠 GAP-7 — `CandidateSavedToTalentPoolIntegrationEvent.EmployerId` is wrong

**Spec ref:** §8.1 (`CandidateSavedToTalentPool` payload: `EmployerId = UserId`)

In `Shortlist.AddCandidate`, the integration event is raised with `EmployerProfileId` as `EmployerId`. The spec explicitly requires `EmployerId` to be the **BC-1 `UserId`**, not the `EmployerProfileId`. The `Shortlist` aggregate only knows `EmployerProfileId`; the `UserId` must be resolved in `AddCandidateToShortlistCommandHandler` and passed into the aggregate (or included in the event from the handler layer).

**Impact:** BC-3 (job seeker notified of shortlisting) and BC-9 (notification) receive the wrong identifier and cannot correlate back to the BC-1 user.

---

### 🟡 GAP-9 — Integration tests use in-memory DB, not a real container DB

**Spec ref:** §13.3

`PersistenceTests.cs` uses `UseInMemoryDatabase`. The in-memory provider does not enforce unique indexes, does not run schema migrations, and does not validate SQL constraints or optimistic-concurrency semantics. The spec explicitly requires "real database in a container" for integration tests.
